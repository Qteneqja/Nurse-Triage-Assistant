# Voice Pipeline Operations

How ORCA's telephony layer works today and how to operate it. Current reality is
**Twilio `<Gather>` (TwiML, request/response) + Twilio STT + Azure TTS** — there is no
streaming pipeline and no ConversationRelay yet (see ADR 0002 for the planned direction).

## When to load this skill

Changes to `src/twilio/routes.py`, `src/security/twilio_signature.py`,
`src/utils/azure_tts.py`, voice config vars, or anything touching how a call is captured,
transcribed, spoken, or fed into the orchestrator.

## How telephony works today

All voice webhooks live in [src/twilio/routes.py](../../../src/twilio/routes.py) under an
`APIRouter` whose every route depends on `validate_twilio_signature`
([routes.py:52](../../../src/twilio/routes.py#L52)):

- `POST /api/v1/voice/incoming` ([routes.py:1417](../../../src/twilio/routes.py#L1417)) —
  inbound call; creates the session, returns TwiML with the first `<Gather>`. Redelivered
  webhooks replay the original TwiML (idempotent).
- `POST /api/v1/voice/gather` ([routes.py:1639](../../../src/twilio/routes.py#L1639)) —
  receives Twilio's `SpeechResult` (+ optional `Digits`), advances scripted intake, then
  hands dynamic turns to the orchestrator.
- `POST /api/v1/voice/thinking` ([routes.py:1994](../../../src/twilio/routes.py#L1994)) —
  poll loop that plays typing sounds while a background LLM turn runs, then returns the
  next TwiML.

**Speech capture:** TwiML `<Gather input="speech dtmf">` generated by
`generate_twiml_gather()` ([routes.py:701](../../../src/twilio/routes.py#L701)) with
`speechModel="phone_call"` and `enhanced="true"` hardcoded, per-stage `timeout` /
`speechTimeout`, and domain `hints`.

**Text into the orchestrator:** the gather handler loads the session by `CallSid`,
appends the caller turn to `session.conversation`, and kicks off the background turn
(`_run_turn(session, speech_text)` → `get_workflow_engine().handle_turn(...)`,
[routes.py:1925](../../../src/twilio/routes.py#L1925)). The orchestrator's safety gates
apply unchanged — the voice layer never makes a triage decision.

## STT / TTS

- **STT:** Twilio built-in speech recognition via `<Gather input="speech">`. No config
  var; to change it you must change the pipeline (see ConversationRelay below).
- **TTS:** Azure Cognitive Services in [src/utils/azure_tts.py](../../../src/utils/azure_tts.py)
  (`synthesize_speech()` → SSML → MP3 → Azure Blob → SAS URL played via `<Play>`). If
  `AZURE_SPEECH_KEY` is unset or Azure fails, it falls back to Twilio Polly
  (`_TTS_VOICE = "Polly.Ruth-Neural"`, [routes.py:457](../../../src/twilio/routes.py#L457))
  via `<Say>`.

**Voice config vars** (`src/config.py`): `AZURE_SPEECH_KEY`, `AZURE_SPEECH_REGION`,
`AZURE_TTS_VOICE`, and Birchwood overrides `BIRCHWOOD_AZURE_TTS_VOICE|RATE|PITCH|STYLE|BREAK_MS`.

**To swap TTS:** reimplement `synthesize_speech()` for the new provider (keep the
`text_to_speech_url()` contract) or force the Polly fallback by not setting `AZURE_SPEECH_KEY`.

## Webhook security

`validate_twilio_signature()` ([src/security/twilio_signature.py](../../../src/security/twilio_signature.py))
verifies the `X-Twilio-Signature` header (HMAC-SHA1 over URL + sorted POST params,
constant-time compare). Controlled by `TWILIO_AUTH_TOKEN`, `TWILIO_WEBHOOK_BASE_URL`
(reverse-proxy URL), and `TWILIO_VALIDATE_SIGNATURE` (off in development, on in
staging/production by default).

## Pipeline selection flag — current state

**There is NO voice-pipeline selection flag.** All calls use Twilio `<Gather>`. There is
no `VOICE_PIPELINE` / ConversationRelay switch in the code. If/when ConversationRelay is
added (ADR 0002), introduce a flag (e.g. `ENABLE_CONVERSATION_RELAY`) and branch TwiML
generation in the incoming handler so rollback is a flag flip.

## ConversationRelay migration — PLANNED, not implemented

No code references `ConversationRelay` or audio streaming today. Phase 4 notes record
that Twilio voice integration is mocked in tests
(`docs/phase4/known_limitations.md`). The intended direction (lower latency, barge-in,
streaming STT/TTS) and its tradeoffs/rollback are captured in
[docs/decisions/0002-voice-pipeline-direction.md](../../../docs/decisions/0002-voice-pipeline-direction.md).

## Running a staged / simulated call (no Twilio)

```bash
# Feed scripted caller turns through the orchestrator; prints traces + dispositions.
python -m scripts.simulate_calls --mock              # no LLM API
python -m scripts.simulate_calls --scenario chest_pain
python -m scripts.run_insurance_demo                 # offline vertical demo
```
The simulator exercises the orchestrator + safety gates directly, so it's the fastest way
to validate a voice/flow change without a live call. For a real staged call, see
[STAGING_RUNBOOK.md](../../../STAGING_RUNBOOK.md) and
[docs/BIRCHWOOD_CALL_TEST_CHECKLIST.md](../../../docs/BIRCHWOOD_CALL_TEST_CHECKLIST.md).

## Rollback path

- Voice pipeline choice is **not** stored per session; TwiML is generated fresh per
  webhook, so a config/flag change affects only new calls (in-flight calls finish on the
  old behavior).
- TTS provider change → revert `src/utils/azure_tts.py` / config and restart.
- Signature regression → `TWILIO_VALIDATE_SIGNATURE` controls enforcement.
- A future ConversationRelay rollout should be guarded by a flag so revert = flip to off.
